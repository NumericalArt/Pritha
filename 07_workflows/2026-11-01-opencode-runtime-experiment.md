# Отложенный план эксперимента с OpenCode

Статус: **deferred**, по решению пользователя от 2026-11-01. OpenCode остаётся
потенциальным проектом со статусом watch. Pritha использует принятый,
проверенный транспорт Codex CLI; пилот и интеграция сейчас не планируются.

План ниже сохранён только для возможного будущего пересмотра. Он не является
активным поручением, очередью работ или разрешением запускать эксперимент.
При возвращении к теме сначала обновить источники и подтвердить конкретную
потребность относительно текущего транспорта.

## Границы пилота

Зафиксировать проверенную версию OpenCode, модели и настройки. Использовать
отдельное disposable workspace и instance-local state. Запускать отдельный
ограниченный процесс; не подключать общий пользовательский сервер.
Проверить реальные пути sessions, credentials, cache и logs до модельного
вызова. Не копировать пользовательские секреты и private memory.

Подготовить внешнюю изоляцию файлов и сети с тестовыми canary-файлами.
Внутренние tools и shell не должны обходить Pritha host approvals.
Существующий host-tool MCP можно изучить как точку интеграции; поддержку
нового исполнителя нельзя считать доказанной до проверки.

## Парное сравнение

Использовать пять заранее определённых заданий:

1. Объяснение устройства небольшой части проекта с проверяемыми ссылками.
2. Исправление ограниченной ошибки с внешним тестом результата.
3. Изменение UI с заранее заданной визуальной проверкой.
4. Обработка синтетического материала в signal и assessment.
5. Небольшой фрагмент child-agent реализации по фиксированной спецификации.

Для каждого задания выполнить по два прогона каждым исполнителем:
20 прогонов всего. Это малый пилот, не статистическое доказательство.
Начинать с одинакового commit, входного контекста, модели при доступности,
инструментов и бюджета. Различия протокола и settings записать явно;
сравнение разных моделей не выдавать за сравнение только исполнителей.

Считать долю результатов, принятых независимым verifier; время и полную
стоимость проверенной задачи; повторы; ручные вмешательства; нарушения
границ; качество возобновления. Отсутствующие usage не заменять нулями.

## Обязательные проверки интеграции

- Отказ, просроченный approval и approval другой сессии не разрешают действие.
- Stop завершает принадлежащие задаче процессы, включая shell descendants.
- Потерянный ответ, reconnect и повторный submit не дублируют исполнение.
- После перезапуска восстановлена правильная сессия; состояние сверяется
  по API, а не только по живому event stream.
- Файлы, история и credentials из другого instance недоступны.
- Контекст после compaction сохраняет обязательные ограничения задачи.
- Недоступность модели и лимит квоты дают различимые ошибки.

## Решение по результатам

Сначала требуются все проверки границ и recovery. Затем оценить хотя бы
один измеримый выигрыш: новые необходимые модели, меньше ошибок протокола,
меньше ручной работы или ниже стоимость при сопоставимом качестве.

Только после этого рассмотреть OpenCode driver для новых Task Chat сессий.
Разделить идентичность исполнителя и поставщика модели; смена default
не должна подменять runtime существующего чата.
Сохранить прежние thread bindings и при неподтверждённых возможностях
показывать ограничения явно. Общую готовность всех connectors не выводить
из успеха одного runtime.

Переход по умолчанию, миграция истории и deployment являются отдельными
решениями. Материальный конфликт с Good State Baseline требует обсуждения
конкретного изменения, а не общего разрешения на исследование.

# Аудит параллельной работы в Task Chat

Возможность реализуема без замены основного runtime. Сервер уже хранит активные
запуски по чатам и может обслуживать несколько тредов одновременно. Основная
доработка — независимость отправок и навигации в интерфейсе, защита от
одновременных повторов запросов и наблюдение за задачами вне выбранного чата.
Для параллельного изменения одного проекта отдельно нужна политика рабочих
каталогов и общих ресурсов.

Это аудит и предложение для обсуждения. Изменение продуктового кода, запуск
новых задач модели, создание служб и deployment в объём этой работы не входят.
Даты артефакта указаны по локальному времени; проверка проходила 2026-09-08 UTC.

Дополнение 2026-09-08: [проверка совместной работы с Voice Control](2026-09-08-task-chat-voice-concurrency-audit.md)
выявила обход busy-thread через CLI fallback, разрыв владения между этапами
Voice-задачи и гонку обновления private bindings. Для общего Voice + Task Chat
scope оценка первого этапа уточнена до 5–9 рабочих дней; 3–5 дней ниже относятся
к более узкому Direct Chat scope и не покрывают все эти пересечения.

## Нужное пользователю поведение

1. В треде A идёт задача. Пользователь открывает существующий B или создаёт C,
   пишет и отправляет сообщение; новая задача начинает работу до завершения A.
2. Переключение между чатами сохраняет их черновики и вложения. Поздний ответ
   на отправку в C не переключает пользователя обратно из B.
3. Ошибка отправки в одном чате не блокирует отправку в остальных.
4. Список показывает, какие задачи работают, завершились или требуют внимания,
   даже когда их переписка не открыта.
5. Сообщение в сам работающий A — отдельная возможность: уточнение текущей
   задачи либо явно отложенное следующее сообщение. Это не второй независимый
   активный turn внутри того же треда.

## Что уже есть

| Участок | Наблюдение по коду |
| --- | --- |
| Gateway | `activeTurns`, leases, события и подписчики хранятся по `chatId`. Нет общего запрета на второй активный чат. `startTurn` возвращается после подтверждения старта, не после завершения задачи. |
| App Server | Одно соединение на provider; несколько незавершённых RPC различаются по request ID. Один процесс App Server сам по себе не означает последовательное выполнение всех тредов. |
| Черновики | Текст и вложения уже разделены по ключу чата в памяти React. Есть отдельные сведения о неопределённой доставке в существующие чаты. |
| Навигация | Смена чата закрывает браузерную подписку и отменяет загрузку старой истории. Она не вызывает остановку серверного turn. |
| Private registry | Записи сериализуются и сохраняются атомарно внутри экземпляра store. Это очередь коротких записей метаданных, а не очередь выполнения задач. |

Основание: `gateway.ts:185`, `gateway.ts:795`, `gateway.ts:1009`,

## Находки и их приоритет

### F1. Общая блокировка отправки — P2, подтверждено кодом

`sending` является одним флагом на всю страницу. Пока HTTP-запрос отправки A
не завершился, Send в B тоже отключён. Для обычного текста это период до
подтверждения старта, а не всё время работы модели; клиентский timeout — 30 секунд.
Для команд бюджета длительность зависит от соответствующей операции.

`pendingNewChatDelivery` дополнительно запрещает Send во всех чатах и создание
следующего нового чата. После неопределённой доставки первого сообщения
ограничение может сохраняться до сверки запроса. Textarea соседнего загруженного
чата при этом доступна: ввод текста и отправка имеют разные ограничения.

Основание: `CodexChatPage.tsx:310`, `:1043`, `:1103`, `:1152`, `:1337`, `:1532`,
`:1571`. Требуется заменить общую блокировку состояниями конкретной отправки
и конкретного draft/chat, сохранив защиту от повторов.

### F2. Одновременный повтор создания может запустить две задачи — P1, воспроизведено

`createThread` сначала ищет `clientThreadId`, затем асинхронно создаёт native
thread и только после этого сохраняет binding. Между проверкой и созданием
нет блокировки по идентификатору запроса. HTTP route проверяет равенство ключа
и `clientThreadId`, но не сериализует этот участок.

В изолированном эксперименте два перекрывающихся вызова
`createThreadWithFirstTurn` с одинаковыми `clientThreadId`, `clientMessageId`
и телом создали **два native thread и два native turn**. Реальный Gateway и
private store использовались с синтетическим runtime; оплачиваемых запусков
не было. Это доказанный дефект пути конкурентного повторения, а не утверждение,
что обычная отправка из интерфейса всегда дублирует задачу.

Основание: `gateway.ts:278`, `gateway.ts:336` и
`src/app/api/codex-chat/v1/threads/route.ts:40`.
Нужны атомарное резервирование ключа до native create и общий результат для
одинаковых запросов в полёте. После сбоя с неизвестным результатом резервирование
нельзя просто удалить и повторить side effect: требуется сверка native history
и сохранённого attempt. Новый механизм должен покрывать и первый turn.

### F3. Позднее создание чата перехватывает навигацию — P2, подтверждено кодом

Успешный `deliverNewChatMessage` без проверки актуальности выбора устанавливает
выбранный чат, группу, transcript и URL. Если пользователь уже перешёл в другой
тред, ответ старого запроса вернёт его в только что созданный чат. Также имеется
единственный ключ нового черновика; несколько создаваемых разговоров он не
различает. У обычной отправки в существующий чат проверка выбранного `chatId`
уже есть, её принцип можно расширить.

Основание: `CodexChatPage.tsx:1082`, `:1121`. Нужны независимые временные draft ID
и проверка версии навигации перед изменением видимой панели. Результат фоновой
отправки должен обновлять её запись, даже если пользователь смотрит другой чат.

### F4. Фоновая активность видна неполно — P2, подтверждено кодом

Браузер подписывается на события выбранного чата. Обновление списка происходит
после ряда локальных действий, событий выбранного треда, focus/online/visibility
и изменений фильтра. Надёжного потока статусов всех работающих Direct Chats нет.
Завершение A, пока открыт тихий B, может не обновить строку A до следующей сверки.
Сервер сохраняет событие и состояние, но это не гарантирует немедленное обновление UI.

Основание: `CodexChatPage.tsx:750`, `:776`, `:815`, `:903`, `gateway.ts:1127`.
Для v1 достаточно ограниченного обновления краткого списка, пока есть активные
задачи; альтернатива — единый SSE поток summary-событий. Не требуется постоянно
загружать полную историю каждого чата. Это обновление открытого интерфейса,
не service watchdog или scheduled automation.

### F5. Отдельные треды используют общий checkout — условие безопасного внедрения

У Direct Chat `threadDefaults()` задаёт один `cwd: this.root`. Отдельные
`chatId` и native thread ID не изолируют файлы, Git index, порты, процессы и
внешние системы. Два анализа могут выполняться независимо; две правки одних
файлов способны конфликтовать. Короткая очередь записей chat registry этого
не предотвращает.

Основание: `app-server.ts:545`, `gateway.ts:295`. Для задач разработки нужны
отдельные Git worktree либо сериализация писателей в общий workspace. Worktree
изолирует файлы checkout, но не общую БД, сервисы, credentials и внешние действия;
для таких ресурсов нужны отдельные правила владения. Existing Outcome Delivery
уже использует свой контракт worktree и lease по run; его проверки не следует
считать общей изоляцией всех Direct Chats.

### F6. Lease ограничена процессом и provider — P2, подтверждена граница защиты

Ключ — `providerId:nativeThreadId`, хранилище — модульный `Map`. Эксперимент
подтвердил, что разные providers получают leases на одинаковый native ID
одновременно. При этом модель storage identity уже допускает один Codex home
для разных providers. Это недостаточность координатора как общей защиты;
двойная запись реальными Codex binaries в один rollout в аудите не проверялась.

Основание: `native-turn-coordinator.ts:1`, `storage-identity.ts`,
`private-store.ts:46`, `realtime/codex-task/codex-app-server-client.ts:168`.
Для общего storage ключ должен учитывать storage identity и native thread ID.
Гарантии между Voice, Task Chat, разными Node workers и внешним Codex требуют
отдельной проверки владельца. Нельзя масштабировать текущий in-memory registry
на несколько серверных процессов и считать файловый atomic rename достаточным
для согласованного read-modify-write.

## Предлагаемый первый этап

Сохранить один управляемый Gateway и существующий App Server transport.
У каждого существующего чата и нового черновика — собственные текст, вложения,
отправка, ошибка и сверка доставки. Оставить один активный turn на native thread,
при этом разрешить независимые треды. Исправить F2 до снятия UI-блокировок,
добавить защиту навигации F3 и обновление статусов F4.

Предлагаемый начальный лимит — три параллельные задачи на экземпляр с явным
состоянием ожидания либо понятным отказом при заполнении. Это продуктовый выбор
для первого испытания, не измеренная аппаратная или Codex-граница. Лимит должен
исполняться сервером; лимиты модели/аккаунта и ресурсы машины остаются общими.
Ввод черновиков и переключение чатов не должны зависеть от свободного слота.
Автоматическая отправка очереди — отдельный явно видимый контракт.

Для анализа и задач в уже разделённых проектах подходит общий runtime. Для
произвольной одновременной разработки в одном проекте сначала определить
политику F5. Новая распределённая очередь и отдельный процесс на каждый Direct
Chat для начального решения не требуются. Общий App Server сохраняет общий
домен отказа: его потеря затронет несколько тредов, а не только выбранный чат.
Синхронные cold probes (`spawnSync` генерации схем и версии) также могут
задерживать весь Node event loop; это отдельный пункт измерения под нагрузкой.

## Сообщение в работающий тред

Официальная документация описывает `turn/steer` как добавление ввода в текущий
turn. Требуется `expectedTurnId`; новый `turn/started` не приходит. Если активного
turn уже нет, запрос отклоняется. Параметры модели и workspace этим вызовом
не меняются. Это требует отдельной обработки истории, подтверждений и гонки
между завершением задачи и доставкой уточнения.
Источник: [Codex App Server, Turns](https://learn.chatgpt.com/docs/app-server#turns).

В схемах установленных bundled `0.153.4` и standalone `0.153.0` есть
`TurnSteerParams` с обязательными `threadId`, `expectedTurnId`, `input`, а также
`TurnInterruptParams`. В текущем Gateway/HTTP/UI соответствующие Direct Chat
действия не реализованы; наличие capability-флага не означает готовую функцию.
Кроме того, `normalize.ts:270` выбирает первый `userMessage` в turn, а `:184`
исключает остальные user messages из списка items. Для отображения отправленных
уточнений потребуется изменить модель представления истории, а не только добавить route.

Следующий этап может добавить явные действия «Уточнить текущую задачу» и
«Отправить после завершения». Нельзя неявно превращать уточнение в новый turn
после ошибки `expectedTurnId` или считать queued-сообщение уже применённым.
Полноценное управление задачей также требует отдельной кнопки остановки с
привязкой к точному turn. Общая система approval/input из контракта в core v1
реализована не полностью: App Server client отвергает server-initiated requests
как unsupported. Расширение интерактивных запросов увеличит объём этапа.

## Трудоёмкость и альтернативы

Оценка инженерная, не обязательство по сроку: один разработчик, знакомый с кодом,
один экземпляр, без redesign и переноса в NeuralDeep. Дни означают полные рабочие
дни с тестами и review. Результаты не являются измерением пропускной способности.

| Вариант | Оценка | Что получаем / ограничение |
| --- | --- | --- |
| Только локализовать UI-флаги | 0,5–1 день | Убирает часть неудобств; F2 и безопасная работа с файлами остаются. Недостаточно для заявления о готовности. |
| Надёжная работа нескольких разных чатов | 3–5 дней | Независимые отправки/черновики, защита создания и навигации, статусы, начальный лимит, конкурентные и браузерные сценарии. Для общего checkout нужна заранее выбранная политика писателей. |
| Уточнение активного turn, остановка и очередь внутри треда | дополнительно 2–4 дня | Отдельные delivery receipts, история уточнений, гонки завершения и UI. Полный approval/input UX оценивается отдельно. |
| Автоматическая изоляция задач разработки | дополнительно 5–10 дней | Worktree lifecycle, привязки существующей истории, ресурсы, перенос результата и восстановление. Не включает распределённых workers. |
| Отдельный процесс на каждый чат / распределённая очередь | отдельный проект | Лучше изоляция отказов, но больше процессов, хранилищ, locks и сопровождения. Для исходного запроса пока избыточно. |

Рекомендация экспертных ролей: Architecture — trial на существующем Gateway;
Security — изоляция писателей и защита повторов; DX — воспроизводимые гонки и
сохранение черновиков; Product — сначала несколько независимых чатов. Новые
внешние зависимости не обязательны. Привязка к Codex App Server сохраняется;
перенос на другого provider потребует адаптации протокола и тестов. Параллельность
может сокращать общее ожидание независимых задач, но не обещает ускорения каждой
задачи и увеличивает одновременно используемые ресурсы и темп расхода лимитов.

## Доказательства и критерии приёмки

В аудите выполнены:

- 38/38 существующих профильных тестов: Codex Chat, Chat Evolution, thread
  routing и continuation. Часть проверок статическая, поэтому этот результат
  сам по себе не доказывает полноценный параллельный пользовательский сценарий.
- Отдельный временный harness использовал реальный транспилированный Gateway,
  private store и синтетический runtime. Подтверждены две одновременно активные
  задачи, отказ второму turn того же чата, адресность delta-событий, сохранение
  задач после unsubscribe и независимое завершение. Отдельно воспроизведена F2
  и проверена граница lease F6. Повторно вызванные fixture-тесты также прошли.
- `codex --version` и генерация JSON-схем обеих установленных версий во временные
  каталоги; чтение официальной документации. Реальные model turns не запускались.
- Good State Alignment для Task Chat / Control Center: два релевантных baseline.
  Аудит и предложенные исправления классифицированы как `aligned`, при сохранении
  native history, private storage, отсутствия автоматического replay и managed lifecycle.
- Markdown validation прошла для 830 файлов с тремя предупреждениями о ранее
  существовавших дубликатах ID в instance-local материалах. Strict privacy audit
  tracked-файлов и отдельная проверка нового review прошли; новый YAML корректен.
  Продуктовый код и работающий runtime не изменялись, индексы памяти не пересобирались.

Для реализации обязательны браузерные сценарии: A работает → запуск B и C;
отправка A задержана → B доступен; потеря подтверждения C → B доступен;
поздний ответ C не меняет выбранный B; переключение сохраняет текст и вложения;
одинаковый concurrent create создаёт ровно один thread/turn; завершение/ошибка/
остановка A не влияет на B; Voice и Direct не пишут одновременно в один native
thread; reconnect/reload не дублирует запрос; фоновое завершение отражается в
списке. Отдельно проверить лимит задач, shared-workspace conflicts и server restart.

Нагрузочный прогон реальных модельных задач, фактическая скорость, UI на телефоне,
полный self-test и проверка deployed fleet не выполнены в этом аудите. Перед
реализацией рекомендован свежий `node scripts/self-test.mjs`; найденный снимок
в legacy memory layout старше семи дней и не является оценкой состояния
текущего production runtime. Для выпуска применимы typecheck/build, desktop/mobile,
privacy audit и strict health с `/codex` и JavaScript chunks по staged-release workflow.
